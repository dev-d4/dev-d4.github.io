01 — About

Vague problem in, working system out

Most of what I've built started as something badly defined. Someone in the business describes a problem in their own words, compliance has a constraint nobody wrote down, and the vendor's system does almost the right thing. My job is to ask the questions that sharpen that into something buildable, and then come back with a system that runs. At Säkra VP that's how the client risk model happened: the logic in Python against a SQL database, deployed on Azure, released through a GitHub Actions pipeline that runs the test suite before anything reaches production. It classifies tens of thousands of clients continuously and the business acts on the output directly, so a wrong result is visible to real people — not just to me.

I've spent most of my time in the seams between systems: integrations with external financial systems, file deliveries, debugging that spans our own data, the vendor's platform and a third party, where it's rarely obvious up front which of the three is wrong. Working those out is the part I've gotten genuinely good at, and it's most of what makes an unfamiliar codebase tractable.

sharpa.se is the one I built because I wanted it to exist. I couldn't compare funds on risk-adjusted return without doing the arithmetic myself every time, so I built the thing that does it: the ingestion and data model, the risk and return engine on top, the interface in Next.js and React, Postgres underneath, deployed on Vercel. There was nobody to hand the hard parts to. I use Claude and Codex daily, which is a large part of why one person can build and maintain it alongside a full-time job — and why I get into code I've never seen before faster than I used to.
